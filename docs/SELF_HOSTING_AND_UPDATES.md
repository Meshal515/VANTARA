# VANTARA — الاستضافة الذاتية والتحديثات الموزعة

> **النوع:** مقترح معماري مستقبلي، وليس ميزة منفّذة. **المراجعة:** 25 أكتوبر 2026.
> هذه الوثيقة لا تعدل كودًا أو تنشر خدمات أو تفتح تسجيلًا عامًا. التنفيذ الحالي يعتمد على مسارات إنتاج خاصة، ولا يصح اعتباره جاهزًا تلقائيًا للاستضافة لكل مستخدم.

## القرار المقترح

**نواة إصدار واحدة، ونسخ مستقلة بالكامل عند المستخدمين.**

ينشر فريق VANTARA إصدارات عامة وموقعة/متحققًا منها، بينما يملك كل صاحب مساحة حساب Cloudflare وقاعدة البيانات وروابط التطبيق وتكاليف التشغيل. لا تحتاج جهة تطوير VANTARA الدخول إلى حساباته أو دفع تكلفة جلساته.

في الشكل المستهدف، يُنشَر **Worker مع Static Assets** لكل مساحة، ويقدّم:
- واجهة PWA وملف `sw.js` من نفس الأصل.
- مسارات API والهوية والمزامنة ذات الصلة.
- الربط بقاعدة D1 وDurable Objects الخاصة بصاحب المساحة.
- صفحة إعداد مستقلة وإعدادات خاصة بالمساحة.

يستطيع الأصدقاء دخول رابط مساحة يملكها صديق واحد، ولا يحتاج كل عضو إلى إنشاء حساب Cloudflare.

```text
       مستودع VANTARA الرسمي + Releases + Manifest + بصمات
                          │
                          ▼
               قناة تحديث عامة للقراءة فقط
               (لا حسابات أو بيانات خاصة)
                          │
          ┌───────────────┼─────────────────┐
          ▼               ▼                 ▼
   نشر Cloudflare A  نشر Cloudflare B  نشر Cloudflare C
   pwa-a.example     pwa-b.example     pwa-c.example
   Worker+PWA        Worker+PWA        Worker+PWA
   D1 + DO خاصة      D1 + DO خاصة      D1 + DO خاصة
   أسرار منفصلة       أسرار منفصلة       أسرار منفصلة
```

## لماذا لا نكتفي بتغيير ملفات الويب من خادم مركزي؟

- كل مساحة لها **Origin** مستقل؛ تسجيل Service Worker لعنوان آخر لا يعمل داخل هذا النطاق. يجب تقديم `sw.js` من أصل الرابط نفسه.
- قد تعجز الواجهة الأحدث عن التواصل مع API قديم. واجهة PWA وخدمة الحسابات وعقود البيانات بحاجة إلى توافق مُعرّف.
- لا يمكن لمستودع VANTARA الأصلي دفع تحديثات إلى آلاف حسابات Cloudflare المختلفة دون إذن وآلية نشر خاصة بكل حساب.
- «تحديث متاح» مجرد إشعار؛ النشر إلى حساب المستضيف عملية تحتاج صلاحية مفوّضة من صاحب الحساب.

## المعمارية المقترحة للتحديثات: VANTARA Update Network

### 1. قناة إصدار رسمية — بلا بيانات مستخدمين

- ينشر VANTARA إصدارًا غير قابل لتغيير محتواه بعد النشر، مع `version` و`commit` وبصمات SHA-256 وملفات `worker` و`pwa` ومعلومات التوافق والترحيلات المطلوبة.
- تعرض القناة بيانات أحدث إصدار مع قناة stable/beta وسياسة `minSupportedVersion`.
- تحقق من سلامة المصدر والبصمة؛ الأفضل اعتماد توقيع إصدار وعميل تحقق موثوق، لأن ملف JSON أو قيمة SHA من نفس المصدر وحدهما لا تمنع اختراق هذا المصدر.
- لا تخزّن قناة التحديث بيانات الأصدقاء أو مفاتيح Cloudflare أو إعدادات المساحات الخاصة.

### 2. وكيل نشر تابع للمستخدم

يوجد خياران قابلان للتطوير:

**المرحلة الأولى — GitHub/Cloudflare Git integration:**
- يتم إنشاء نسخة من قالب النشر تحت حساب GitHub للمستخدم، مع ربطها بمشروع Cloudflare الخاص به.
- إعداد مزامنة موثوق يكتشف الإصدارات الرسمية ويقدّم/ينفذ تحديثًا على نسخته بحسب سياسة المستخدم.
- تندمج التحديثات الموثوقة في فرع النشر الخاص به، فتتولى Cloudflare نشر Worker والأصول.
- لا نعتمد على افتراض أن تحديث المستودع الرسمي يصل آليًا إلى جميع forks؛ يحتاج ذلك تدفق مزامنة صريحًا.

**المرحلة المتقدمة — Update Agent:**
- يختار المستضيف تفعيل أداة نشر محدودة الصلاحية تعمل داخل حساب GitHub/Cloudflare الذي يملكه أو عبر تفويض مقيد.
- تتأكد الأداة من الإصدار والتوقيع والتوافق وتُجري اختبارات Preflight، ثم تنشر النسخة وتتحقق من نجاحها.
- لا نحفظ مفاتيح حسابات المستضيفين في VANTARA المركزي ولا نطلب مفاتيح API شاملة داخل صفحة ويب عامة.
- عند تعذر التشغيل التلقائي تظهر خطوات تحديث يدوي، ولا تُوقف النسخة القديمة ما دامت مدعومة وآمنة.

### 3. نشر PWA وWorker كتوزيعة مترابطة

- الأفضل استهداف **Cloudflare Workers Static Assets** لتقديم `index.html` و`sw.js` والملفات الأصلية ومسارات API من عنوان واحد عند كل مستضيف.
- يحتفظ كل مستخدم بالرابط نفسه عبر جميع التحديثات؛ لا يُنشأ نطاق جديد لكل إصدار.
- تُحفَظ بيانات الإضافات وحسابات المستخدمين منفصلة عن ملفات البرنامج العامة.
- لا يتحول التحديث إلى إعادة تعيين للمكتبة أو البيانات المحلية أو نقلها إلى حساب صاحب المشروع.

### 4. بروتوكول التوافق

لكل إصدار:
- `appVersion` و`workerVersion` و`schemaVersion`.
- `minCompatibleWorker` و`minCompatibleApp` وبيان قدرات API.
- ترحيلات D1 متدرجة وإضافية وآمنة لإعادة التنفيذ، مع بوابة تمنع تشغيل نسخة غير متوافقة.
- نسخ احتياطي أو مسار استعادة موثوق قبل أي ترحيل غير عكسي، واختبارات على نسخة بيانات مشابهة.
- فحص API والدخول والمزامنة وWebSocket وتجهيز غرفة وصحة صفحات PWA قبل الترويج إلى الإنتاج.
- إذا فشلت التهيئة لا يُعلن نجاح التحديث. أما الرجوع إلى نسخة Worker سابقة **فلا يعيد بيانات D1 تلقائيًا**، ويحتاج سياسة توافق/استعادة منفصلة.

### 5. طريقة تحديث PWA للمستخدم النهائي

بعد نشر حزمة مساحته:
1. يصبح `sw.js` الجديد متاحًا من أصل النطاق نفسه.
2. يتحقق المتصفح من تحديث عامل الخدمة ويحمّل الموارد بحسب سياسة الكاش.
3. يظهر تنبيه «تحديث متاح»، دون تغيير الصفحة أو قطع القراءة/المشاهدة الجارية.
4. يُفعّل التحديث عند اختيار المستخدم أو بعد إغلاق الجلسة، مع الحفاظ على البيانات المحلية.
5. تُسجّل النسخة العاملة ويظهر إجراء إعادة محاولة عند تعذر التحميل.

## سياسات كل مساحة

| السياسة | السلوك |
| --- | --- |
| **تحديثات تلقائية مستقرة** | نشر إصدار Stable بعد اختبارات التوافق والصحة وتحقق المصدر |
| **مراجعة قبل التحديث** | مستضيف المساحة يؤكد التحديث؛ مناسب للإصدارات التي تغير العقود أو البيانات |
| **إصدار مُثبّت** | يحتفظ بالنسخة الحالية حتى يختار المستضيف التحديث، ضمن فترة دعم محددة |
| **قناة تجريبية** | تحديثات أسرع مع تحذير أنها ليست للإنتاج |
| **فشل التحديث** | بقاء الإصدار المستقر السابق وعدم تحريك مستخدميه إلى نسخة مكسورة |

**التوصية:** لا تجعل الترحيلات المدمرة أو تغييرات الأذونات ضمن تحديث صامت تلقائيًا.

## اختلاف أجهزة Android وWindows

- يصدر التطبيق الأصلي من **قناة التوزيع الرسمية** كالمعتاد؛ لا يلزم أن يبني كل مستضيف نسخته الخاصة من Android أو Windows.
- يتصل التطبيق بواحد أو أكثر من عناوين المساحات المصرح بها، بعد إكمال آلية الربط والتحقق من هوية المساحة.
- تختلف نسخ التطبيقات الأصلية عن إصدارات Worker/PWA؛ تضمن مصفوفة التوافق استمرار التطبيق القديم خلال نافذة انتقال مدروسة.
- بيانات كل مساحة لا تُدمج مع غيرها بمجرد تحديث التطبيق العام.

## لماذا هذا أفضل من تحديث كل مساحة يدويًا؟

- كود ومراجعة إصدار واحد، وتوزيع آلي بتفويض كل مستضيف.
- تكلفة Worker وD1 وDO تقع على المستضيف، ولا تُنقل تفاعلات مستخدميه إلى حساب المطور.
- قابلية إصلاح أمني جماعي دون مشاركة بيانات أو مفاتيح المالكين.
- قدرة كل مساحة على التأجيل والرجوع عند وجود خلل، بما لا يخالف أمن الإصدارات المدعومة.

## حدود الوضع الحالي التي تتطلب عملًا

وفق الكود الحالي في `main`:
- `apps/web/lib/config.js` يحتوي عنوان مزامنة إنتاجيًا افتراضيًا، وتحتاج النسخة المستضافة ذاتيًا اختيار endpoint موثوقًا دون توجيه المستخدم خطأً إلى خادم التجربة.
- `services/sync-worker/wrangler.toml` يحدد Worker/D1/DO خاصًا بالبيئة الحالية ويحتاج قالبًا قابلًا لإعداد أسماء وموارد مستقلة.
- `.github/workflows/sync-worker.yml` يعمل لحساب النشر الحالي؛ لا يُنقل كما هو إلى مفاتيح حسابات الآخرين.
- `apps/web/sw.js` و`apps/web/pwa/update.js` يحتاجان اختبار تحديث متعدد الأصول وتوافق API بنسخ مختلفة.
- `services/sync-worker/src/secure-index.ts` ونظام الهوية يحتاجان عزلًا صريحًا بين المساحات ودعواتها.
- إعداد التحديث لا يعني أن Cloudflare Workers/Pages يدعمان النشر التلقائي إلى حساب آخر دون صلاحية. وميزة **Deploy to Cloudflare** تدعم Workers وموارد مختلفة، لكن لا تدعم إعداد Pages/monorepo الكامل كما هو تلقائيًا.

## ترتيب التطوير عند البدء لاحقًا

1. اختبار عزل مساحة تشغيل واحدة وإزالة التوجيه الافتراضي إلى حساب المطور في نموذج الاستضافة الذاتية.
2. تصميم حزمة Worker + Static Assets تحتوي واجهة PWA وAPI المناسبين على أصل واحد.
3. إنشاء قالب `Deploy to Cloudflare` مع إعداد D1 وDO وأسرار منفصلة.
4. بناء manifest للإصدارات ومصفوفة توافق واضحة.
5. تجربة مزامنة تحديث تلقائية لمستضيفين وهميين وحسابين مستقلين، مع اختبار فشل النشر.
6. اختبار ترحيلات D1 وعمليات الاستعادة والانقطاع أثناء جلسة مشاهدة.
7. إضافة سياسة تحديثات اختيارية وآلية تحديث التطبيقات الأصلية.
8. نشر دليل استضافة ذاتية ومعلومات التكاليف والحدود التشغيلية.
