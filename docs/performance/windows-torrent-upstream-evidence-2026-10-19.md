# Windows torrent startup: upstream evidence, 2026-10-19

## Supported decisions

Keep the shipped rqbit integration for the first startup repair. A direct selected-file add when the exact file index is known avoids duplicate magnet resolution. Reusing exact-hash metadata and a bounded managed torrent can improve subsequent openings. **Stock rqbit 9.0.1 fastresume is not an integrity-preserving persistent-cache solution:** the local reproduction below demonstrates corrupted bytes being served after restart.

Acceptance targets supplied for this investigation are 2–10 seconds from click to first visible frame, under 2 seconds for warm close/reopen, and under 10 seconds after app restart. These are targets, not measured results. A title, “4K”, size, or advertised seed count does not establish the same torrent. Comparisons require exact info hash and file index, comparable peers/network, and documented cache state.

Research only: no production engine changes, merge, release, or publication are included. No whole engine or proprietary source is copied into this branch.

## Persistence, fastresume, and verified pieces

CLI supports `server start <stable-output> --persistence-location <app-owned-state> --fastresume` ([main.rs:305](https://github.com/ikatson/rqbit/blob/a499d2f243d124e144aef137afe7cb304a6e3f36/crates/rqbit/src/main.rs#L305), [735](https://github.com/ikatson/rqbit/blob/a499d2f243d124e144aef137afe7cb304a6e3f36/crates/rqbit/src/main.rs#L735)). Removing current --disable-persistence alone retains metadata but still uses a nonpersistent bitfield and initial checksum validation on restart.

JSON store writes session.json, hash.torrent, and, for fastresume, hash.bitv ([json.rs:116](https://github.com/ikatson/rqbit/blob/a499d2f243d124e144aef137afe7cb304a6e3f36/crates/librqbit/src/session_persistence/json.rs#L116), [188](https://github.com/ikatson/rqbit/blob/a499d2f243d124e144aef137afe7cb304a6e3f36/crates/librqbit/src/session_persistence/json.rs#L188)). Restore uses TorrentFileBytes when present ([mod.rs:40](https://github.com/ikatson/rqbit/blob/a499d2f243d124e144aef137afe7cb304a6e3f36/crates/librqbit/src/session_persistence/mod.rs#L40)). Both forget and delete remove persisted torrent bytes and bitv through session deletion; forget only keeps payload ([json.rs:257](https://github.com/ikatson/rqbit/blob/a499d2f243d124e144aef137afe7cb304a6e3f36/crates/librqbit/src/session_persistence/json.rs#L257)). Forget/re-add does not retain verified state.

Fastresume [initializing.rs:86](https://github.com/ikatson/rqbit/blob/a499d2f243d124e144aef137afe7cb304a6e3f36/crates/librqbit/src/torrent_state/initializing.rs#L86) checks bitfield byte length, selects at least the first possessed piece per file, then up to 64 candidate pieces with decreasing probability. There is no stored mtime/size manifest validation in this routine. **Line 157 tests only check_piece(...).is_err().** [FileOps::check_piece](https://github.com/ikatson/rqbit/blob/a499d2f243d124e144aef137afe7cb304a6e3f36/crates/librqbit/src/file_ops.rs#L186) returns Ok(false) on hash mismatch, so that corruption passes. Correcting that branch would still leave sampling unable to prove arbitrary changed pieces unchanged.

Without usable bitv, [file_ops.rs:117](https://github.com/ikatson/rqbit/blob/a499d2f243d124e144aef137afe7cb304a6e3f36/crates/librqbit/src/file_ops.rs#L117) walks all pieces and hashes existing file ranges. Sparse allocation does not make a 26 GiB logical selected file cheap to hash: holes read as zeros. Missing files can be skipped after read error, while present sparse files retain logical ranges. Thus rechecking is a real restart-latency concern.

Safe implementation boundaries:

1. Same-process unchanged owned payload can reuse a bounded managed handle. Stop player readers independently; never retain hole-punched pieces as verified. Use lease/handle/byte/free-space limits.
2. Metadata reuse across processes removes magnet resolution, not payload checks.
3. Cross-process payload requires full recheck or a separately reviewed verified-byte/piece cache with explicit invalidation before serving. A bounded HTTP extent cache populated only from rqbit verified streams can serve its retained bytes without trusting a stale rqbit bitv; it must key exact hash+file+offset and protect storage/identity/atomic writes. That design is separate from this research and its performance remains to be measured.

Stock v9.0.1 HTTP has no per-piece invalidation, forced recheck, or deadline API. Whole inactive-torrent deletion is easier to coordinate than modifying live piece storage.

### Exact telemetry fields

`GET /torrents/{id}/stats/v1` has `live.snapshot.peer_stats.{seen,queued,connecting,live,live_tcp,live_utp,live_socks,dead,not_needed,steals}` ([source](https://github.com/ikatson/rqbit/blob/a499d2f243d124e144aef137afe7cb304a6e3f36/crates/librqbit/src/torrent_state/live/peers/stats/mod.rs#L12)). `seen` counts discovered peers; `live` counts current live connections. `live.snapshot.{fetched_bytes,downloaded_and_checked_bytes,downloaded_and_checked_pieces,total_piece_download_ms}` separates wire traffic from newly completed verified pieces. `live.download_speed.mbps` is MiB/s, despite its name; multiply by 1024 squared for bytes/sec ([stats.rs](https://github.com/ikatson/rqbit/blob/a499d2f243d124e144aef137afe7cb304a6e3f36/crates/librqbit/src/torrent_state/stats.rs#L233)).

Top-level progress_bytes means bytes checked during Initializing and possessed selected bytes in Live/Paused ([state mapping](https://github.com/ikatson/rqbit/blob/a499d2f243d124e144aef137afe7cb304a6e3f36/crates/librqbit/src/torrent_state/mod.rs#L522)); do not label initialization progress as downloaded data. `GET /haves` with `Accept: application/octet-stream` returns Msb0 bits and X-Bitfield-Len total piece count. For first-selected-piece telemetry compute its global piece index from file offset, rather than assuming bit zero. `added.details.total_pieces` is an actual response field ([api.rs](https://github.com/ikatson/rqbit/blob/a499d2f243d124e144aef137afe7cb304a6e3f36/crates/librqbit/src/api.rs#L542)).

## Comparison engines: applicable ideas and rejected assumptions

**Rivulet, former stremio-server-go:** [engine reader](https://github.com/rivulet-kodi/rivulet-engine/blob/841b5506c84817b02b6eb8efa79d9b7a5f1cc080/internal/engine/engine.go#L1366) uses adaptive readahead; [warmMoov](https://github.com/rivulet-kodi/rivulet-engine/blob/841b5506c84817b02b6eb8efa79d9b7a5f1cc080/internal/engine/engine.go#L1415) detects MP4 moov before mdat and skips tail warming for faststart. [Manager add](https://github.com/rivulet-kodi/rivulet-engine/blob/841b5506c84817b02b6eb8efa79d9b7a5f1cc080/internal/engine/engine.go#L533) accepts metadata bytes. VANTARA mappings: metadata/add lines 503/564, warmEdges 574, cleanup 370. Adapt session reuse and conditional probing, not anacrolix reader knobs unavailable in rqbit HTTP. A source comment about MKV tail Cues is not proof every MKV requires its tail before first frame; inspect actual mpv byte requests.

**andrewhack:** [boost/refocus](https://github.com/andrewhack/stremio-libtorrent-server/blob/71a446a9c08d603a50690ca97d05379751c31f0f/src/stremiosrv/torrent/engine.py#L491) combines priority 7, deadlines, and removal of old playhead urgency while protecting the viewer from secondary-reader deadline changes. [fileserver](https://github.com/andrewhack/stremio-libtorrent-server/blob/71a446a9c08d603a50690ca97d05379751c31f0f/src/stremiosrv/stream/fileserver.py#L100) waits on have_piece and never reads past the verified piece, avoiding sparse zeros. VANTARA mapping: proxy/windowTick. Adapt the verified-byte invariant and missing-piece telemetry; these libtorrent calls are not rqbit HTTP options.

**stremio-native:** [libtorrent stream priorities](https://github.com/stremio-native/stream-server/blob/f585ab6eda9b1411034548c131bb0dc30c6f5f9e/enginefs/src/backend/libtorrent/stream.rs#L147) distinguish container metadata from user scrub/streaming. [Playback permits](https://github.com/stremio-native/stream-server/blob/f585ab6eda9b1411034548c131bb0dc30c6f5f9e/enginefs/src/backend/libtorrent/playback.rs#L69) coordinate windows. Optional [librqbit readiness](https://github.com/stremio-native/stream-server/blob/f585ab6eda9b1411034548c131bb0dc30c6f5f9e/enginefs/src/backend/librqbit.rs#L317) simply labels readiness librqbit-reader; it does not expose libtorrent deadlines. VANTARA mapping: competing warmEdges/player reads. Engine replacement adds packaging/ABI/dependency work; no measured result here justifies it as the first repair.

**libtorrent:** [streaming.rst](https://github.com/arvidn/libtorrent/blob/d22c5efb3e9ebcf1950d56a8279b0625ae1225af/docs/streaming.rst#L9) explains why sequential pieces can still block: a slow peer owns the needed early piece while fast peers fetch later pieces. Deadlines actively choose peer queue slots for urgent pieces; [API](https://github.com/arvidn/libtorrent/blob/d22c5efb3e9ebcf1950d56a8279b0625ae1225af/include/libtorrent/torrent_handle.hpp#L423) exposes set/reset/clear but cannot guarantee arrival. VANTARA mapping: aggregate download-speed stall detection is insufficient. This supports controlled uneven-peer tests, not an unmeasured engine-switch promise.

## Verification needed for the targets

Record a monotonic click→engine-ready→metadata→file-selected→managed-add→HTTP-headers→first-body-byte→decoder-frame→visible-presentation timeline. A successful POST, file-loaded event, peers, or high transfer rate does not establish a visible frame.

Use authored faststart MP4, moov-at-end MP4, and MKV fixtures. Compare same exact hash/file with fast peer, mixed fast/slow peers, and constrained bandwidth; cold/warm/restart states; direct add versus duplicate resolution; player-led versus conditional prefetch; retained Live versus retained Paused. Test overlapping readers and backward seek into evicted pieces for stale verified-state zeros. Linux loopback findings require packaged Windows rqbit/mpv frame measurements before reporting targets met.
