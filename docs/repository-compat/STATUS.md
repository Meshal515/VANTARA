# حالة الدفعة الأولى — نواة تجريبية مستقلة

## ما نُفذ فعليًا

- دراسة15 بلاغًا مختارًا وردوده، مع تثبيتSHAs للمشاريع وتمييز البلاغ/المقترح/الإصلاح المذكور في الرد. ليست مراجعة جميع بلاغاتهم أو إثباتًا لثغرات أمنية فيهم.
- Package Gate أصلي يقرأZIP/DEX دون تشغيله أو استخراج ملفات إلى الجهاز، ويتحقق من الحد والبصمة وCRC وتواقيع DEX ونقطة الدخول وحدود جداول البيانات.
- عقدHost أصلي للكتالوج والبحث والتفاصيل والفصول/الحلقات/الصفحات وروابط الفيديو. الـbackend اعتماد صريح؛ غيابه أو غياب وظيفة لا يصبح مصدرًا عاملًا. تسجيل Backend لا يعني صحة المصدر.
- سياسة نطاق مشتركة بين الإضافات، وRetry-After رقمي/تاريخ، وحالة تحقق حسب الجلسة، وإلغاء/مهلة لا يحرران فتحة النقل قبل انتهائه الفعلي. لا إعادة طلب آلية ولا إشعار UI أو تشغيل متصفح.
- هوية النقل تأتي في سياق منفصل ثابت من الـhost، ولا يستطيع request استبدالها. لا يتلقى backend مخازن الحسابات أو متحكم تذاكر التحقق.
- نتائج التشخيص منفصلة لكل قدرة؛ نجاح الكتالوج لا يمسح خطأ البحث، والنتيجة الفارغة ليست نجاحًا وظيفيًا. لا تشغيل لمحرك torrent أو subtitle/translation/player في هذه الطبقة.

## الفحوص الحالية

- Node:26 اختبارًا، منها منع تزوير سياق النقل واشتراك النطاق بين إضافتين وعدم خلط جلسات التحقق وإلغاء النقل غير المتعاون.
- Python:16 اختبارًا، منها حد ذاكرة64MiB في عملية منفصلة لاستنساخ تضخيم metadata داخلDEX، ورفضه برسالة DEX_METADATA_LIMIT بدل OOM.
- فحص حزم AnimeWitcher وAnime4Up وAnimeRift وWitAnime الفعلية بأربعةpins وبـcommit ثابت: نجح فحص التنسيق والبصمة ونقطة الدخول. لم تُشغَّل الحزم ولم تُطلب مواقع المصادر.
- حارس النطاق: إضافات ملفات فقط؛ كل الملفات الموجودة في التطبيق المنشورf20723d محفوظة، بما فيها التورنت والمشغل والترجمة والمصادر والحسابات والمزامنة.

## ما التقطته المراجعة وصُحح قبل الدفع

1. سياق المصدر والجلسة كان يضيع عند الوصول للنقل المشترك، ويمكن لحقول الطلب تزويره. أعاد اختبارRED إنتاجه؛ صار السياق immutable وسيطًا منفصلًا، والطلب محدد الحقول.
2. أرشيف صغير يستطيع تكرار مراجع سلاسلDEX وتضخيم الذاكرة بعد فك الضغط. أعاد اختبارRED إنتاج فشل الحدود؛ أُضيفت ميزانية إجمالية مشتركة لكلDEX في الحزمة، وتخزين للسلاسل المعادة، وحساب كلفة prototypes/references قبل بنائها، وفكUTF16 إلىbuffer محدود بدل قائمة كائنات كبيرة. فحص64MiB نجح.

## ما لم يُنفذ بعد — ليست هذه الدفعة Runtime CloudStream مكتملًا

- لاAndroid worker أو isolatedProcess/InMemoryDexClassLoader أو ABI implementations حتى الآن. لا وجود لاختبار تشغيل cs3 على جهاز، ولا نتائج catalogue/search/playback حية.
- Executor المستخدم في اختباراتHost مؤلف للاختبار فقط. استثناء backend منطقي محصور، لكن OOM/segfault لعامل Native غير مختبر ولا يُدّعى عزله.
- النقلHTTP الفعلي وDNS/TLS/redirect enforcement لكل قفزة غير مضافين هنا. البوابة والسياسة ليستا sandbox أو ضمانًا لعدم حظرIP.
- لا تركيب في الواجهة أوAPK، ولا تعديل أو ترحيل بيانات أو تغيير محرك افتراضي. لم يُمس Stable المنشور.
- لا تشغيلDEX فيPWA/Windows بمجرد قبول الحزمة. لكل منصة ملف توافق مطلوب واختبار تنفيذ مستقل.
- لا cache للردود الخاصة ولا إدارة تثبيت/تحديث ذرية أوفصل للمصادر المدمجة في هذه الدفعة؛ تلك مراحل لاحقة تستلزم اختبارات انقطاع وترقية ورجوع.

## الخطوة التقنية التالية

بناء ملف ABI محدد للحزم الأربع من API_REQUIREMENTS.json والمراجع الرسمية، مع دلالات فعلية وليستno-op stubs، ثم عامل Android منفصل بصلاحيات مقيدة ونقل مملوك للـhost. يلزم إثبات تسجيلMainAPI وتشغيلبحث/كتالوج/تفاصيل/حلقات/استخراج روابط في اختبار فعلي. وصولActivity المباشر فيAnime4Up وgetBaseClient فيAnimeRift يحتاجان معالجة صريحة؛ لا تجاوز silent للبروكر أو تقديمActivity الرئيسية.
