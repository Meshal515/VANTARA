# تقرير إصلاح تحديث Windows وتكامل إضافات التورنت — 26 أكتوبر 2026

المصدر: `c5741f01` (main عند بدء العمل). فرع العمل: `fix/windows-update-release-parity-20261026`.

## سبب رجوع التحديث المثبت

كان `apps/web/desktop/update-check.js` يقرأ `windows-channel/desktop-update.json` فقط رغم نشر ملفات Windows مع Stable. يشير هذا المؤشر إلى السلسلة المنفصلة 0.3.18. المقارنة الرقمية تعتبر 0.3.18 أحدث من 0.0.209؛ ولذلك تعرض محتوى أقدم لمستخدم Stable. لم يكن مسار IPC يفحص اتجاه انتقال الإصدار بصورة مستقلة.

أضيفت اختبارات تعيد إنتاج الحالة قبل الإصلاح. أصبح المصدر الأساسي بيان Stable الموحد، مع مؤشر آخر مثبت Windows مكتمل عند تأخر بناء Windows عن APK. ترفض Stable أي رجوع للقناة المنفصلة، ويحرس main التنزيل والتثبيت أيضًا. تُفحص هوية ملف المثبت ووسمه ورقمه وبصمته وحجمه.

العائلة التالية المقترحة `0.4.N` موحدة بين Android وWindows والواجهة، لتجاوز المقارنة القديمة لـ0.3.18 حتى على الأجهزة التي لم تتلق الإصلاح بعد. يبقى رقم Android الداخلي ووسم stable-N متزايدًا كما هو؛ N يحدده تشغيل الإصدار الحقيقي. لم يُنشر إصدار بهذه العائلة أثناء هذا التحقق.

## سياسة الإصدار

أزيل تشغيل Android Stable التلقائي بعد CI على main. يُنشأ Stable بواسطة workflow_dispatch من main فقط، بعد فحص تطابق المصدر مع main الحالي ووجود CI ناجح لنفس SHA وقبل استعمال أسرار التوقيع. تبقى فحوص التوقيع والتحقق من الملفات.

يبنى Windows companion بعد Stable المختار صراحة. لا يُحدّث مؤشر Windows حتى تثبيت المثبت وفحص المحرك والتحقق من الملفات المنشورة. تُسلسل عمليات النشر عبر الإصدارات لمنع سباق يعيد المؤشر إلى الوراء، ويرفض المولد رقمًا أقدم أو استبدال مثبت منشور مختلف تحت الرقم نفسه. هذا لا يوقف نشر الويب والخدمات المعتاد؛ يفصل إنشاء Stable تحديدًا.

## تكامل الإضافات

ثبت اختلاف قبول مصادر التورنت عن Android: نتيجة تحتوي `magnet` فقط، وBTIH Base32، و`url: magnet:` كانت تُفقد في التكييف أو اختيار مصدر Windows. جرى توحيد تحويل الهوية إلى BTIH hex، مع حفظ fileIdx (بما فيه الصفر) وtrackers والترجمات. ترفض الهويات المتعارضة وروابط Magnet ذات معاملات المصادر الخارجية غير المسموحة. الواجهة المشتركة تعطي APK وPWA أيضًا نفس تحقق الهوية دون منح PWA محرك BitTorrent غير موجود.

## التحقق حتى هذه النقطة

اختُبرت نسخة معزولة من الملفات المرحلية، دون إدخال عمل محرك الوكيل غير المكتمل:

- الواجهة: 1731 اختبارًا في 195 ملفًا، كلها ناجحة.
- السلامة والتحديث وبيانات الإصدار: 68 اختبارًا، كلها ناجحة.
- منها 14 اختبارًا لمسار المثبت وبيان الإصدار وتقدم قناة Windows.
- فحص YAML لملفي إصدار Stable وWindows companion ناجح.
- تحديث بصمة قشرة service worker حسب محتوى الملفات؛ لا تتطلب إزالة بيانات المستخدم.

هذه النتائج تثبت عقود التحديث وتكامل الإضافات. لا تثبت زمن أول إطار على Windows أو شبكة تورنت عامة. لا توجد هنا مقارنة أداء عامة قبل/بعد ولا ادعاء أن تأخر التورنت أُصلح نهائيًا. اختبار المحرك الحقيقي والتغليف وWindows CI مسار منفصل قيد التنفيذ.

لا تشمل التغييرات حذف الحسابات أو البيانات المحلية أو تغيير هوية الجهاز أو إعدادات الإضافات الشخصية.

## فحص التثبيت الحقيقي على Windows

نجح [Windows update recovery verification](https://github.com/Meshal515/VANTARA/actions/runs/40337503406) من commit `30b61014`: بُني مثبت اختبار 0.4.214، ثم جرى تنزيل مثبت Stable209 الحقيقي والتحقق من حجمه وSHA256، وتثبيته قبل تمرير المثبت الجديد عبر مسار downloadUpdate والتحقق من بايتاته ثم تشغيل NSIS الفعلي.

تقرير [recovery-report.json](verification/windows-update-20261026/recovery-report.json) يثبت تطابق package وBUILD-MANIFEST وconfig وDisplayVersion بعد التحديث، وبقاء ثلاث علامات بيانات اختبار، ورفض الرجوع أو إعادة تثبيت الرقم نفسه، وصحة مسار يحوي العربية والمسافات. نقل المثبت الجديد في الاختبار محلي من CI؛ لم يُعرض هذا الرقم كتحديث إنتاجي ولم نختبره كتحديث شبكة منشور للمستخدم.
